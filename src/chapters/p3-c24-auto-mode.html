Auto mode

確認の代わりに別の分類器モデルが操作を審査するモードです。使える条件と分類器のモデル、判定順、既定のブロックと許可、しきい値とサブエージェントの扱い、サーバー側レビューと課金、autoMode 設定と関連コマンドを扱います。モードの一覧と開始モードは Ch23 を参照してください。

使える条件と分類器のモデル

  • 全プランで使えます。Team・Enterprise でも既定で有効で、管理者は managed の permissions.disableAutoMode: "disable" で止めます（トップレベルの disableAutoMode も可）。
  • 管理者配布の設定が届くと、実行中のセッションも auto から抜け auto mode disabled by settings と表示します（v2.1.251 以降）。
プロバイダ対応モデル

Bedrock、Agent Platform、Foundry、Claude apps gatewaySonnet 5 以降、Opus 4.7 以降、Haiku 5.5（v2.1.293 以降）、Fable
どこでも非対応Sonnet 4.5、Opus 4.5、Haiku 4.5、claude-3

  • defaultMode: "auto" は project・local 設定では効きません。~/.claude/settings.json に書きます。

判定順と、auto に入ると外れる allow ルール

各操作は固定の順で判定され、最初に当たった段で決まります。

  1. allow・ask・deny ルールで即決。例外: 保護パスの書き込みは allow があっても分類器へ。クリティカルパス削除は allow で承認されない。requiresUserInteraction・組織 ask のツール、内容で絞った ask（Bash(git push *)）、ネットワークパスの読み取りは確認。ホストを指定したコマンドは分類器へ。
  2. 読み取りと作業ディレクトリ内の編集は自動承認。保護パスと、作業ディレクトリ外の初回読み取りは除く。サーバー側レビューがあると、読み取り専用とサンドボックス内のシェルコマンドもレビューを待つ。
  3. それ以外は分類器へ。クリティカルパス削除は既定では分類器に行かない。
  4. ブロックされると Claude に理由が届く。多くは [Data Exfiltration] のようなルール名。

auto に入ると外れる allow ルール

  • Bash(*)・PowerShell(*)、Bash(python*) のような interpreter のワイルドカード、パッケージマネージャの run コマンド、Agent の allow、Monitor の allow（v2.1.236 以降）。auto を出ると戻ります。
  • Bash(npm test) のような狭いルールは残ります。autoMode.classifyAllShell: true にすると、Bash・PowerShell の allow をすべて止めて全シェルコマンドを分類器に回します。

分類器が見るもの

  • ユーザーのメッセージ、ツール呼び出し（読み取り系の照会を除く）、CLAUDE.md。ツール結果は除かれます。
  • PostToolUse フックの classifierContext で結果に注記できます（v2.1.236 以降）。
  • git reset --hard や rm -rf の前に Claude Code が git status を実行し、未コミットの作業の有無を分類器に見せます。
  • SendMessage で別のエージェントに送る内容も審査します（v2.1.222 以降）。

既定でブロックするもの・許可するもの

分類器が信頼するのは作業ディレクトリと、開始時に設定済みのリモートだけです。主な既定ブロック（全文は claude auto-mode defaults）:

  • curl | bash などの取得と実行、機密データの外部送信
  • 本番デプロイ・マイグレーション、クラウドストレージの大量削除、IAM・リポジトリ権限の付与
  • force push、git reset --hard・git clean -fd など未コミットの作業を捨てる操作、push 済みコミットの --amend
  • terraform destroy 系、シークレット・DNS・TLS 証明書の変更、本番 feature flag
  • 未承認 PR のマージ、自分の PR の承認、CI の無効化、ChatOps コメント
  • --insecure 系フラグ、--dangerously-skip-permissions などで起動するエージェント
  • /tmp の glob 削除、トランスクリプトへの書き込み、指名のない git remote set-url
  • v2.1.257 以降: 169.254.169.254 の資格情報、迂回経路、隣のコンテナの走査

既定で許可

  • 作業ディレクトリ内のファイル操作、ロックファイルやマニフェストにある依存のインストール
  • .env を読み、資格情報を対応する API に送ること、読み取りだけの HTTP
  • 作業中リポジトリの任意のブランチへの push（デフォルトブランチを含む）。production・gh-pages のようなデプロイ用の名前は除く
  • 同じセッションで作ったジョブの削除、セキュリティ関連の作業、同一セッション内のエージェント間メッセージ

会話で伝える境界と承認

  • 「don't push」のような境界は、解除するまでブロックの根拠になります。ルールとして保存されず毎回トランスクリプトから読むので、圧縮で消えることがあります。確実にするには deny ルールを使います。
  • 承認は操作と危険の具体（force push ならブランチ）を名指しします。「you can force-push」だけでは解除されず、効くのは 1 回の操作です。
出典: permission-modes#what-the-classifier-blocks-by-default · #boundaries-you-state-in-conversation · #approvals-you-state-in-conversation

ブロック後の扱い・しきい値・サブエージェント

  • ブロックすると通知を出し、/permissions の Recently blocked に載せます。通知の形式は bash blocked by auto mode · /permissions · Auto mode: [Data Exfiltration] です。
  • 連続 3 回か合計 20 回ブロックすると auto mode は止まり、確認に戻ります。確認した操作を承認すると auto に戻ります。しきい値は変更できません。合計はセッション中保持され、自身の上限で戻ったときだけリセットされます。
  • --permission-prompt-tool のない -p ではその操作だけ実行されず、Claude は作業を続けます。安全確認自体ができずに拒否された場合、-p は exit 1 で終わります（2.1.319）。
  • 分類器から判定が返らないときは、通知も Recently blocked もなくブロックします。サーバーが判定を返さないときは拒否し、10 回連続でターンを止めることがあります。
  • 確認中にモードを切り替えると、新しいモードが求めない判定は捨てられ、確認（dontAsk なら拒否）になります。

作業ディレクトリ外の初回読み取り

Read・Grep・Glob が初めて外を読むとき 1 度だけ確認します（-p とバックグラウンドでは出ない）。

  • Yes, and keep allowing any reads outside the working directories
  • No, and block reads outside the working directories from now on: user 設定に permissions.blockReadsOutsideWorkingDirectories: true を書く
  • No, and ask again next time / Yes, but ask again next time

サブエージェント

  1. 開始前: 委譲するタスクの説明を審査
  2. 実行中: 親と同じ判定順とルールで各操作を審査。frontmatter の permissionMode は無視
  3. 終了時: 作業と最終報告を審査。問題があれば報告の先頭に警告を付けて渡す

autoMode の設定: スコープ・4 段階・"$defaults" (1/2)

  • 分類器は ~/.claude/settings.json、managed settings、--settings・SDK のインライン JSON から autoMode を読みます。リポジトリが allow を差し込めないよう、.claude/settings.json と .claude/settings.local.json は読みません。
  • 各スコープのエントリは連結されます。開発者は managed のエントリを消せませんが、開発者の allow は組織の soft_deny を上書きできます。絶対に止めるには managed の permissions.deny を使います。
  • キーは environment・allow・soft_deny・hard_deny（正規表現ではなく文章の配列）と classifyAllShell（既定 false）です。分類器は CLAUDE.md も読みます。
段分類器内での働き
hard_deny無条件にブロック。ユーザーの意図も allow も効かない
soft_deny次にブロック。意図と allow で解除できる
allow一致する soft_deny の例外
明示の意図まさにその操作を具体的に頼んだときは残りの soft_deny を解除。「clean up the repo」は force push を許さない

docs の例の抜粋です。allow 節を省き、各文を … で切っています。

{
  "autoMode": {
    "environment": [
      "$defaults",
      "Source control: github.example.com/acme-corp …"
    ],
    "soft_deny": [
      "$defaults",
      "Never run database migrations outside the migrations CLI, …"
    ],
    "hard_deny": [
      "$defaults",
      "Never send repository contents to third-party …"
    ]
  }
}

"$defaults" は組み込み一覧をその位置に差し込みます。書かないとその節を置き換え、soft_deny なら force push や curl | bash、hard_deny ならデータ持ち出しのルールを失います。
